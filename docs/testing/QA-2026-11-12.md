## 2. Qué cubre la suite automatizada (al 12 nov)

- **238 pruebas unitarias** (Jest): sesión/JWT, reglas de cada feature (chat, entregas, mentores,
  controles del educador, avisos, interruptores, registro de actividad), matriz de permisos de las
  ~32 rutas protegidas (sin sesión → 401, sesión del rol equivocado → rechazado, un educador no ve
  el evento de otro, sesión revocada → rechazada).
- **113 pruebas end-to-end** (Playwright), dos modos:
  - `@readonly`: contra cualquier URL (local o desplegada) sin tocar la base real — login, i18n,
    layout en 3 tamaños de celular × 4 idiomas, pantallas guardadas (`/mestre`, `/jogador`,
    `/mentor` sin sesión).
  - `@db`: un evento completo de punta a punta contra la base real — educador se registra, crea
    sesión, dos jugadores entran y arman un equipo, contestan fases, chatean, el educador manda
    avisos y carta de reto, activa interruptores de emergencia, un mentor entra y califica, **el
    educador lo quita y su calificación deja de contar**, se exportan los 3 CSV, se cierra el
    evento.
- Corrida completa (`pnpm typecheck && pnpm lint && pnpm test && pnpm exec playwright test && pnpm
build`) repetida **tres veces** la noche del 12 nov sobre ramas distintas (`dev`, la rama de
  sincronización hacia `qa`, y `qa` mismo) antes de autorizar el release a producción — las tres,
  en verde.

## 3. Prueba manual en vivo contra la base real (12 nov, madrugada)

Las pruebas automatizadas usan una base de datos real pero efímera (`E2E_DB=1`, se borra sola). Para
el fix de seguridad de mentores (PR #33) se hizo además una prueba manual en el navegador contra la
base de producción real, porque el pedido explícito era "asegúrate en la base de datos que el
mentor removal jale, debe quedar todo al 100":

1. Educador genera un código de mentor nuevo (`AEAUZS`) en una sesión de prueba.
2. Un mentor ("Juez Intruso Random") entra con ese código, sin aprobación previa — confirma el
   hueco de seguridad original: cualquiera que sepa el código entra.
3. El mentor califica a un equipo (3.0 de promedio).
4. El educador abre "Ver calificaciones de mentores", ve al mentor en la lista, presiona "Quitar" →
   "¿Seguro? Quitar".
5. **Verificado en pantalla:** el mentor desaparece de la lista ("Nadie se ha unido todavía"), el
   equipo vuelve a "Sin calificar".
6. **Verificado con una petición real:** `GET /api/mentor` desde la sesión del mentor ya quitado
   responde `401` — su sesión murió en la siguiente petición, no se esperó a que expirara.

### Bug encontrado y corregido en esta misma prueba

Al construir la UI del paso 4 se usó por error una clave de traducción de otro namespace
(`t("resumo.equipes")` en vez de una clave propia de `educador`), que se manifestó como
`MISSING_MESSAGE` en el overlay de Next.js y texto crudo en pantalla. Se detectó **durante** esta
misma prueba manual (no antes), se corrigió agregando la clave correcta a los 4 diccionarios, y se
repitió la verificación completa de los 6 pasos de arriba antes de dar el fix por bueno. Ver
`docs/prs/PR-33.md`.

## 5. Lo que NO se alcanzó a probar (honesto, sin maquillar)

Todo esto se hizo en menos de una semana junto con el resto del trabajo. No es que se decidiera no
hacerlo — no hubo tiempo para más:

- **Nunca se simuló la base bajo 300-500 personas entrando al mismo tiempo con la configuración
  real de hoy** (Vercel Pro + Supabase tier Small + el `DATABASE_POOL_MAX` actual). La única
  prueba de carga que existe es la del 8 nov (sección 10 de `docs/backend/ESTADO-BACKEND.md`),
  corrida desde una computadora en casa contra Supabase directo, con 300 participantes y 0 errores
  — pero **no** contra el hosting real, y **no** con el código de esta semana encima.
  `pnpm load-test --base https://www.tabuleirodoempreendedor.com` sigue pendiente de correrse.
- **No se probó desde la red/wifi real del lugar del evento.**
- **No se probó en navegadores reales de Android/Firefox**, solo Chromium (Playwright) + Safari/
  Chrome de forma manual en celulares físicos.
- **No hubo una auditoría de seguridad formal** de los cambios de esta semana (sí se revisó
  manualmente inyección SQL — solo se usa `$queryRaw` parametrizado, nunca `$queryRawUnsafe` — pero
  no fue una auditoría completa).
- **No se repitió una revisión de diseño/UX de las ~15 pantallas de la app**, solo se corrigieron
  los bugs puntuales encontrados (ver `docs/frontend/ESTADO-FRONTEND.md`).
- El comportamiento exacto de Vercel Spend Management al tocar el límite de $20 a media carga **no
  se probó** (no es algo que se pueda simular sin gastar el presupuesto real).
